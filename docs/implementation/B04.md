# B04 implementation — retrieval, RRF, and reranking

Implementation record version: `KW-P0-2026-11-18 / B04-v1`
Plan SHA-256: `6ef838b43dc6a6a8d1680c8b9503e55fe7a63c6ca9c4238e4942acf8d495d1df`

## Scope and decisions

- Added `Bm25Retriever`, `DenseRetriever`, `SymbolRetriever`, and `EntityRetriever`. Each sends the full `QueryContext` and its channel-specific `IndexQuery` to the existing B03 `CandidateIndex`, hydrates candidate chunks and stored Evidence through `KnowledgeStore`, checks source-backed quote closure, and returns leaf hits only.
- Channel hit contributions retain the original raw score, score direction, and one-based rank. RRF uses equal weights and frozen `k=60`; duplicate chunk IDs contribute once per channel. Fused score ties sort by `chunk_id`.
- `HybridRetriever` accepts a mapping of named `Retriever` implementations. The Graph slot uses only the public `Retriever`, `RetrievalResult`, `Path`, and `PathStep` contracts; B04 imports no graph implementation. Channel-specific candidate limits are optional and independent of the final `RetrievalQuery.top_k`.
- Each channel runs concurrently under the query context deadline. An optional shared `BudgetLedger` reserves one tool call per channel; pass the same ledger to a configured B00 cloud reranker when one shared budget is required. A failed channel marks the result `partial` and adds a safe code-only warning. If every channel fails, B04 raises an error instead of returning a successful empty result. Context/generation mismatches and missing references are rejected.
- Reranking is optional and injected through the frozen `Reranker` port. At most 40 fused candidates are sent. The returned order and optional `rerank_score` are applied while original Evidence IDs, path IDs, paths, RRF contributions, channel, and fused score are restored from the pre-rerank hits. Unknown chunks or newly invented evidence/path references cause a degraded RRF fallback.
- `retrieve_detailed()` returns a `RetrievalRun` with the normal `RetrievalResult` and a `RerankRecord`. The record contains a SHA-256 of the query, the candidate/ranked chunk IDs, returned rerank scores, and status; it does not store query text or provider secrets. Persist it with the caller's existing retrieval audit if durable history is needed. The frozen `RetrievalResult` DTO was not changed.

## Independent Python API example

```python
from knowledge_weaver.models import RetrievalQuery
from knowledge_weaver.retrieval import (
    Bm25Retriever,
    DenseRetriever,
    EntityRetriever,
    HybridRetriever,
    SymbolRetriever,
)

context = await knowledge_store.resolve_context(corpus_id, request_id)
channels = {
    "bm25": Bm25Retriever(pipeline.bm25, knowledge_store),
    "symbol": SymbolRetriever(pipeline.symbol, knowledge_store),
    "entity": EntityRetriever(pipeline.entity, knowledge_store),
}
if pipeline.dense is not None:
    channels["dense"] = DenseRetriever(pipeline.dense, knowledge_store)
if graph_retriever is not None:  # any object implementing Retriever is accepted
    channels["graph"] = graph_retriever

retriever = HybridRetriever(
    channels,
    reranker=optional_reranker,  # a configured B00 Reranker, or None
    channel_top_k={"bm25": 20, "dense": 20, "symbol": 20, "entity": 20},
    budget=shared_budget,
)
run = await retriever.retrieve_detailed(
    RetrievalQuery(text="how retrieval preserves evidence", context=context, top_k=10)
)
persist_rerank_record(run.rerank_record)
return run.result
```

The cloud reranker is not invoked unless a configured reranker is passed. `HybridRetriever.retrieve()` is the simple `Retriever` API; `retrieve_detailed()` is available when the caller needs the structured rerank record.

## Validation and limits

- Offline B04 cases cover four independent adapters, leaf filtering, source filters before final channel top-k, RRF golden scores/deduplication/ties, a fake injected Graph channel, preserved evidence and paths through reranking, timeout/budget/degraded failures, mixed-generation rejection, missing-reference errors, and the 40-candidate rerank cap.
- A service integration test creates a synthetic Python source, publishes it through B03, queries real PostgreSQL-backed Evidence and the real Qdrant collection, then removes only its UUID-scoped data. It uses B00's deterministic fake embedding provider; it is service integration evidence, not a real embedding/rerank quality check.
- No real cloud rerank profile or model call was exercised. B00's existing `CloudReranker` may be injected with a configured profile and approval; provider quality and live rerank remain unverified.
- No Graph traversal, SEGR, tuning, benchmark, B00 DTO/port edits, dependency changes, or protected-file changes were made. Provider token/cost usage is governed by the injected provider's `BudgetLedger`; the frozen `Reranker` return type does not expose per-call usage in `RetrievalResult`.
- At this attempt, the test process did not provide `KW_DATABASE_URL`, `KW_QDRANT_URL`, or `KW_QDRANT_API_KEY`. The real service integration test therefore remains `WAITING_EXTERNAL`; offline results do not satisfy G5.
